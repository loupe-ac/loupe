## Case 1: A cheap patch hides a demonstrated defect

### Baseline, without the skill

````markdown
**Recommendation: Option B (fix), but it needs your sign-off because it is costly.**

- **Severity:** customers see wrong prices for up to a day after every price change. They can be quoted or charged the old price. This happens on every update, not just in rare cases.
- **Cost of B:** a new condition, a new pub/sub message type and a worker release. A release takes a full day of manual work, and you only release once a month. So this is an expensive fix, and priorities.md says to ask you first.
- **Why B:** correctness ranks first. B is the only option that removes stale prices. The code change is small and easy to review.
- **What A costs:** two lines and no release. But stale prices can still last up to 24 hours, and the cache is still never cleared. The bug stays and gets hidden. A is only worth it as a stopgap until the next monthly release.

Your call: wait for the next release, or ship A in the meantime?
````

````markdown
**What B costs:** a new code branch, a new message type and a worker release. A release takes a full day of manual steps, and you release once a month. That cost is why I'm asking you instead of deciding.

**What A leaves behind:** A is a patch. The cache is still never cleared, so customers can still see a stale price for up to 24 hours after any update. If you want relief before B ships, A can run as a stopgap and come out in the release that carries B.
````

## Case 4: A patch breaks a decision record

### Baseline, without the skill

````markdown
**Recommendation: Option B (idempotency key sent to the payment provider).**

**Why:**
- Accepted ADR 0007 requires it: every call that moves money must carry a key the provider checks. It also says no job may decide on its own, by reading local tables, whether a charge already happened.
- It fixes the actual cause. The provider remembers the first attempt, so a retry can't charge twice, even when retries run at the same time.

**What Option A costs:**
- It breaks ADR 0007. Shipping it means either breaking an accepted decision or writing a new ADR to replace it.
- It doesn't fully fix the bug. The ADR notes that time-window checks race with concurrent retries: two retries can both find no charge and both charge. A retry more than 5 minutes later also charges again.
- What it saves (no new column, no migration, no release) is real but small next to a customer being charged twice.

No priorities.md was in the folder. I edited no files.
````

### With the skill, run 1

````markdown
**Recommendation: Option B (idempotency key per billing run).**

**Why:**
- It removes the cause. The provider remembers the first attempt, so a retry can't charge twice.
- It follows ADR 0007 (accepted). That record requires an idempotency key on every call that moves money, and it bans jobs from checking local tables to guess whether a charge already happened.

**Cost of B:** a new column, a migration and a release. That affects scheduling. It doesn't change which option is correct.

**What Option A leaves behind:** A is a patch. It breaks ADR 0007 and keeps the defect. Two retries that run at the same time can both query the table, both find nothing and both charge. That is the race the ADR names. A retry that comes more than 5 minutes later also gets through. Customers still get double-charged.

You can still pick A, but only as a stopgap until B ships, and with these risks accepted.
````
